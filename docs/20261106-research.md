# Gate research record — 2026-11-06

[← Gate](../README.md)

Status: historical API probes and design proposal. The Rust implementation now covers M0 through M5.
The [current tool contract](tools.md), [configuration](configuration.md), and [limits](still-moving.md)
supersede the proposed language, layout, defaults, and open decisions below.
The implementation uses OpenCode-managed worktrees and locked JSON records instead of the proposed SQLite store.
Live validation found that the worktree API's `branch` parameter selects an existing reference;
omitting it can create a detached HEAD. Gate reports the branch it observes, including `null`.

Research + architecture notes. Everything marked **(verified)** was probed on this
machine against the running OpenCode service, not inferred from docs.

## 1. Problem shape

The orchestrator (Claude Code or Codex) keeps planning, decomposition, review and
final judgement. OpenCode does the actual work: editing files, running shells and
tests, spawning its own subagents.

What the gateway has to solve, in order of difficulty:

1. **Session mapping** — one orchestrator task maps to one durable OpenCode session.
2. **Async execution** — OpenCode prompts return immediately; work continues in the
   background. Codex's MCP tool timeout defaults to **60 s**, so a blocking
   `delegate` tool is not viable.
3. **Streaming progress** — the orchestrator needs incremental output, not a
   silent 20-minute hang.
4. **Permissions** — OpenCode asks before sensitive actions (`shell`, `edit`,
   `.env` reads). Something must answer those prompts.
5. **Parallelism** — several tasks at once means several sessions, optionally
   several git worktrees.
6. **Context economy** — the orchestrator should receive a diff and a summary, not
   50k tokens of transcript.

## 2. What each side exposes

### 2.1 OpenCode (the executor)

`opencode serve` exposes a full HTTP API plus an SSE stream: 170 operations,
described by `/openapi.json`.

**(verified)** Discovery and auth:

- Service URL comes from `~/.config/opencode/service.json`; the daemon was at
  `http://127.0.0.1:49374`.
- Auth is HTTP Basic `opencode:<password>`, where `<password>` is the
  `password` field in `~/.config/opencode/service.json`. Bearer auth is rejected.
- `opencode api get /api/info` works without handling auth.
- `@opencode/client` has `Service.discover()` / `Service.ensure()` /
  `Service.headers(endpoint)`, which is the supported way to find and
  authenticate against the local service from Node.

**(verified)** Prompting is asynchronous:

```
POST /api/session/{id}/prompt  {text, model, agent, files, delivery, resume}
  -> 200 {"data": {"type":"user", ...}}          # admitted immediately
  -> execution continues in the background
```

Wait for idle:

```
POST /api/experimental/session/{id}/wait  -> 204
```

**(verified)** Event stream `GET /api/event` is `text/event-stream` and is a
**global firehose across all projects and sessions**:

```
: heartbeat

data: {"id":"evt_...","created":1793895558866,"type":"session.text.delta",
       "location":{"directory":"/tmp/opencode/spike"},
       "data":{"sessionID":"ses_...","delta":"OK"},
       "durable":{"aggregateID":"ses_...","seq":42,"version":1}}
```

There are **no `event:` lines** — the type lives in the JSON. During the probe the
stream also carried events from this very agent's session in another directory,
so the gateway must filter on `location.directory` *and* `data.sessionID`.

Relevant event types:

```
session.execution.started | .succeeded | .failed | .interrupted
session.step.started | .streamed | .ended | .failed
session.text.started | .delta | .ended
session.tool.input.* | session.tool.called | .progress | .success | .failed
permission.asked | permission.replied
session.idle
session.usage.updated
```

**(verified)** Message history:

```
GET /api/session/{id}/message   -> newest-first
assistant message: {content:[{type:"text",text:"OK"}], model, cost, tokens, finish}
```

**(verified)** End-to-end run: created session → subscribed SSE → posted prompt →
received `session.execution.started` → `session.text.*` → `session.execution.succeeded`,
and the assistant message contained `OK` with `finish:"stop"`.

Other useful endpoints:

| Need | Endpoint |
| --- | --- |
| Create session (agent/model/dir/title/metadata) | `POST /api/session` |
| Switch agent / model mid-session | `POST /api/session/{id}/agent`, `/model` |
| Steer or queue input while running | `POST /api/session/{id}/prompt` with `delivery: "steer" \| "queue"` |
| Interrupt | `POST /api/session/{id}/interrupt?resume=` |
| Turn diff / patch | `GET /api/session/{id}/diff` → `[{file,patch,additions,deletions,status}]` |
| Pending permissions | `GET /api/session/{id}/permission`, `GET /api/permission/request` |
| Answer permission | `POST /api/session/{id}/permission/{requestID}/reply` `{decision:"once"\|"always"\|"reject", message?}` |
| Worktree per task | `POST /api/worktree` `{projectID,name,branch,from}` |
| One-shot, no daemon | `opencode run --format json --session <id>` |

Constraints:

- A session runs **one prompt at a time**; parallel work means parallel sessions.
- `POST /api/session` accepts `parentID`, so child sessions are possible.
- Permission `reject` rejects the pending request **and every other pending request
  in that session**.

#### Corrections found while building (live server 2.1.4)

- The live OpenAPI is served at `GET /openapi.json` (not `/api/openapi.json`) and has
  124 operations, not the 170 in the earlier snapshot. Trust the live document.
- The permission reply field is `decision`, with an optional `message`. Sending
  `reply` fails with `400` because the body schema is `additionalProperties: false`.
- Diff and snapshots are **git-backed**. In a directory that is not a work tree,
  `GET /api/session/{id}/diff` returns `[]` even after the agent wrote files.
  `files[].patch` requires the git snapshot recorded for the turn.
- The default message page is newest-first; pass `order=asc` for chronological
  order. `limit` is a string query parameter.
- `system` messages in a session can be very large (OpenCode injects its own tool
  catalog), so transcripts should filter to `user` / `assistant` / `shell`.
- `POST /api/session/{id}/interrupt` takes `?resume=true|false`; `resume=false`
  stops the turn without replaying pending steering input.
- Absolute directories must exist before `POST /api/session`, otherwise the call
  fails with `LocationNotFoundError`.

### 2.2 Claude Code (the orchestrator)

- MCP client over stdio, streamable HTTP, SSE (deprecated) and WebSocket.
  `claude mcp add`, `.mcp.json`, or plugin `.mcp.json`.
- Tools are exposed as `mcp__<server>__<tool>`; allow/deny via `permissions`.
- **Tool timeouts:** per-server `timeout` (ms) or `MCP_TOOL_TIMEOUT`, default
  **~28 h**. Idle timeout is 5 min for HTTP / 30 min for stdio unless progress
  notifications keep arriving. A main-conversation call still running after
  **2 min** is auto-backgrounded and its result arrives as a task notification.
- Plugin layout: `.claude-plugin/plugin.json`, `commands/`, `agents/`, `skills/`,
  `hooks/hooks.json`, `.mcp.json`, `bin/`. `${CLAUDE_PLUGIN_ROOT}`,
  `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}` are substituted, and
  `userConfig` can prompt for endpoint/token at install time.
- Headless: `claude -p --output-format stream-json`.

Implication: Claude Code alone could tolerate a blocking `delegate` for a long
time, but not indefinitely — progress notifications or the async pattern are still
required.

### 2.3 Codex (the other orchestrator)

- MCP client over stdio and streamable HTTP, configured in
  `~/.codex/config.toml` or project `.codex/config.toml`:
  ```toml
  [mcp_servers.gate]
  command = "gate"
  args = ["mcp"]
  tool_timeout_sec = 3600        # default is 60
  default_tools_approval_mode = "auto"
  ```
- Defaults that matter: `startup_timeout_sec = 10`, **`tool_timeout_sec = 60`**,
  `enabled_tools` / `disabled_tools`, per-tool `approval_mode`.
- `codex exec --json` for headless; `codex app-server` (experimental JSON-RPC)
  for embedding; `codex mcp add` for config; plugins can bundle MCP servers.
- Codex also has native subagents, but they are Codex's own workers, not OpenCode.

Implication: **`tool_timeout_sec` alone forces the async job model.** A `delegate`
that blocks for 10 minutes dies at 60 s unless the user edits their config.

## 3. Why MCP is the seam

| Candidate | Claude Code | Codex | Verdict |
| --- | --- | --- | --- |
| MCP | native | native | ✅ one server, both clients |
| ACP | no | no | ❌ (OpenCode supports it, the orchestrators don't) |
| HTTP/REST tool | no generic tool | no generic tool | ❌ requires custom integration each side |
| Shell-out per task | yes | yes | ⚠️ fallback only: loses streaming, sessions, permissions |

MCP is the only extension protocol both orchestrators speak natively. One stdio
MCP server serves both.

**Do not use ACP.** OpenCode's ACP support is excellent, but neither Claude Code
nor Codex implements an ACP client.

## 4. Architecture

```
┌──────────────────────┐        MCP / stdio         ┌──────────────────┐
│ Claude Code          │ ─────────────────────────► │                  │
│  (planner/reviewer)  │                            │   gate           │
└──────────────────────┘                            │  ┌────────────┐  │
┌──────────────────────┐        MCP / stdio         │  │ MCP server │  │
│ Codex                │ ─────────────────────────► │  ├────────────┤  │
│  (planner/reviewer)  │                            │  │ job/session│  │
└──────────────────────┘                            │  │  registry  │  │
                                                    │  ├────────────┤  │
                                                    │  │ event demux│  │
                                                    │  ├────────────┤  │
                                                    │  │ permission │  │
                                                    │  │  broker    │  │
                                                    │  └────────────┘  │
                                                    └────────┬─────────┘
                                                             │ HTTP + SSE
                                                             ▼
                                                    ┌──────────────────┐
                                                    │ opencode serve   │
                                                    │  sessions, tools │
                                                    │  subagents, wt   │
                                                    └──────────────────┘
```

Design rules:

1. **One process, one MCP server, one OpenCode client.** Stdio transport for v1;
   HTTP transport later if a remote/shared gateway is needed.
2. **Always async internally.** `delegate` starts a job and waits up to a
   caller-supplied budget; if the budget expires it returns a job id plus recent
   progress. Never rely on a single long tool call.
3. **One SSE subscription for the whole process**, fanned out in memory by
   `sessionID`. Reconnecting per tool call would multiply load and lose ordering.
4. **Sessions are the unit of state**, and OpenCode already persists them. On
   restart, re-attach by `sessionID` instead of replaying. A small local SQLite
   table only stores `job → sessionID → directory → status`.
5. **The orchestrator never edits files.** It gets `Read`/`Grep`/`Glob` (or just
   the diff tool). That makes the split real instead of advisory.

## 5. Tool surface (v1)

Names are kept short because Codex and Claude both surface them verbatim.

| Tool | Purpose |
| --- | --- |
| `delegate` | Create a session (or reuse one), post the task, wait up to `wait_ms`, return result or job id |
| `status` | Job state, current step, last N progress events, token/cost so far |
| `wait` | Long-poll a job; returns on completion, permission request, or timeout |
| `messages` | Full/partial transcript for a job |
| `steer` | Send additional instruction to a running session (`delivery:"steer"`) |
| `cancel` | Interrupt the session |
| `diff` | Patch + stats for the job's turn(s) |
| `reply_permission` | Answer a pending permission request |
| `list` | Jobs/sessions for this project |
| `models` / `agents` | Discovery for `delegate` arguments |

`delegate` input:

```jsonc
{
  "task": "string",                  // the work order, incl. acceptance criteria
  "directory": "/abs/path",          // defaults to CLAUDE_PROJECT_DIR / cwd
  "agent": "build",                  // OpenCode agent id
  "model": "anthropic/claude-sonnet-5-5#high",
  "session_id": "ses_...",           // continue an existing session
  "reuse": false,
  "worktree": false,                 // isolate in a git worktree
  "files": [{"uri": "file:///abs/spec.md"}],
  "wait_ms": 45000,                  // budget before returning a job id
  "permission_mode": "auto"          // auto | ask | deny-shell-edits
}
```

`delegate` output:

```jsonc
{
  "job_id": "job_...",
  "session_id": "ses_...",
  "status": "completed | running | blocked_on_permission | failed | cancelled",
  "summary": "final assistant text",
  "diff": {"files": 3, "additions": 42, "deletions": 7},
  "changed_files": ["src/a.ts", "src/b.ts"],
  "pending_permission": null,
  "usage": {"input": 12000, "output": 900, "cost_usd": 0.04},
  "artifacts": ["..."]               // full transcript/diff written to disk
}
```

Deliberate choices:

- **Return a summary, not the transcript.** Claude Code caps MCP output at 25k
  tokens by default. Full logs go to `${CLAUDE_PLUGIN_DATA}`/tmp and are referenced.
- **`wait` returns on permission asks**, not just completion. Otherwise an
  orchestrator that waits for completion deadlocks against the permission broker.
- **`diff` is separate from `delegate`.** The reviewer wants the patch without
  re-reading the session.

## 6. Permissions design

OpenCode resolves every action to `allow` / `ask` / `deny`; `ask` blocks the
session until a client replies. Three gateway modes:

| Mode | Behaviour | Use |
| --- | --- | --- |
| `auto` | Reply `once` to everything except configured `deny` rules | Trusted dev box, MVP |
| `ask` | Surface `permission.asked` through `wait`/`status`; orchestrator decides | Default for real work |
| `human` | Push to an out-of-band channel (TTY, Slack, desktop notification) | Dangerous repos |

Recommendations:

- Encode the real policy in OpenCode agent config (`permissions` list), not in the
  gateway. The gateway should mostly rubber-stamp what OpenCode asks.
- `reject` nukes *all* pending requests in the session — reply `reject` only when
  aborting.
- `always` writes a durable project-scoped allow rule, so use it sparingly.

Example executor policy for a delegated agent:

```jsonc
// .opencode/opencode.jsonc
{
  "agents": {
    "delegate": {
      "mode": "primary",
      "model": "anthropic/claude-sonnet-5-5#high",
      "permissions": [
        { "action": "*", "resource": "*", "effect": "allow" },
        { "action": "shell", "resource": "git push *", "effect": "deny" },
        { "action": "read", "resource": "*.env", "effect": "deny" }
      ]
    }
  }
}
```

## 7. Parallelism and isolation

- 1 job = 1 OpenCode session. N jobs run concurrently; the SSE demux keeps them apart.
- `worktree: true` calls `POST /api/worktree` with the project id and a
  task-specific name, then uses the returned directory as the session location.
  This is the safe mode for parallel edits.
- Inside a session, OpenCode can fan out further with its own `subagent` agents
  (`explore`, `general`, custom). Child session events carry
  `_meta["opencode/child-session"]` over ACP; over SSE they arrive as their own
  `session.*` events with the child's `sessionID`, so subscribe by child id too.

## 8. Context passing

Inbound:

- Task text = objective + constraints + acceptance criteria + file pointers.
- Attachments via `files[].uri` (file paths work).
- OpenCode loads the repo's own instructions (`AGENTS.md`, `.opencode/`, skills)
  from the session directory — do not duplicate them in the prompt.

Outbound (bounded):

- final assistant text,
- tool-call summary (name, target, exit status),
- patch via `/diff`,
- token/cost from the assistant message,
- pointer to full artifacts on disk.

## 9. Tech stack

**Recommendation: TypeScript on Node 24, pnpm.**

| Concern | Choice | Why |
| --- | --- | --- |
| Runtime | Node 24 | installed; both orchestrators ship Node tools; single `node` process per session |
| Language | TypeScript (ESM) | generated OpenAPI types, MCP SDK reference language |
| MCP | `@modelcontextprotocol/sdk` 1.32.x | stdio server, progress + logging notifications, tool schemas |
| Schemas | `zod` 4.x | tool input validation; MCP SDK uses it natively |
| OpenCode client | `@opencode/client` 2.2.x (+ `/service`) | generated from the same OpenAPI contract; `Service.discover/ensure/headers` solves auth |
| Testing | `vitest` | fast, ESM-native |
| Build | `tsup` (esbuild) | one `dist/index.js`, shebang `bin` entry |
| Packaging | npm + `bin: gate` | `npx @you/gate mcp` works from both orchestrators |
| Persistence | `node:sqlite` (built into Node 24) or `better-sqlite3` | job → session map only; OpenCode owns real state |
| Logging | `pino` to file + stderr | stdio MCP means **stdout is protocol only** |

Why not Rust/Go: viable (a single static binary is genuinely nicer to distribute),
and the parent directory is `Dev/rust`. But all three ecosystems are TypeScript,
`@opencode/client` is generated TS, and the MCP server SDK is most complete there.
Rust (`rmcp` + `reqwest` + `tokio`) is a reasonable v2 if binary distribution
becomes the binding constraint. Estimate: 3–5× the integration work for v1.

Why not just `opencode run` per call: no streaming, no steering, no permission
bridge, no session reuse, process spawn per task. Keep it as the degraded fallback
when no daemon is available.

Dependency sketch:

```json
{
  "name": "@you/gate",
  "type": "module",
  "bin": { "gate": "./dist/index.js" },
  "dependencies": {
    "@modelcontextprotocol/sdk": "^1.32.2",
    "@opencode/client": "^2.2.5",
    "zod": "^4.6.7"
  },
  "devDependencies": { "tsup": "^8", "typescript": "^5", "vitest": "^3" }
}
```

## 13. Risks and gotchas

1. **Global SSE firehose.** Events from every project (including the orchestrator's
   own session) arrive on one stream. Filter early and drop unknown sessions before
   they hit any queue. Backpressure matters: buffer per session, never block the
   reader.
2. **Codex's 60 s default tool timeout.** Ship the config snippet; do not assume
   users will edit it. Async job ids are mandatory.
3. **Permission deadlock.** A blocking `delegate` plus an unanswered `ask` hangs
   forever. `wait` must return `blocked_on_permission`.
4. **Model fallback (observed).** Requesting `opencode/deepseek-v4.1-flash-free`
   silently ran `opencode/crouton-alpha-free`. Always report the model that actually
   ran (read it from the assistant message) so the orchestrator does not attribute
   results to the wrong model.
5. **Experimental endpoints.** `/api/experimental/session/{id}/wait`,
   `/experimental/session/{id}/log`, `client-mcp` routes carry no stability
   guarantee. Isolate them behind one module and test on OpenCode upgrades.
6. **MCP output limits.** Claude Code truncates around 25k tokens. Never return a
   full transcript from a tool.
7. **stdout discipline.** stdio MCP uses stdout for JSON-RPC. Every log line,
   warning and stack trace must go to stderr or a file.
8. **Two orchestration styles.** Claude Code backgrounds long calls after 2 min;
   Codex kills at 60 s. The same async contract must serve both.
9. **Duplicate context.** OpenCode already loads `AGENTS.md` and skills from the
   directory. Passing them again in the prompt inflates cost and confuses the model.
10. **Version churn.** Pin `@opencode/client` to the server minor version; the API is
    generated but `experimental` surface moves.

---

## 14. Open decisions

1. **Language**: TypeScript (recommended) vs Rust single binary.
2. **Transport**: stdio per orchestrator (simple, recommended) vs one shared HTTP
   MCP server (better for many concurrent orchestrators, needs auth/port management).
3. **Default permission mode**: `auto` for local dev, `ask` for anything shared.
4. **Scope of v1**: single-repo, or multi-repo with worktrees from day one.
5. **Distribution**: private npm package, Claude Code plugin marketplace, or a
   repo-local `bin/` invoked by absolute path.
